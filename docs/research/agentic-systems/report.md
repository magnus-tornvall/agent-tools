# Replace the coordinator, keep the DAG

The evidence favours the Symphony direction over the current Orca spec on three of its four design choices. Use a deterministic orchestrator rather than an LLM coordinator. Give each agent one objective with one writer per coherent change, rather than splitting work into roles or into parallel slices. Keep repo-resident policy, but keep it short. On the fourth choice, human escalation, Symphony is weaker than the spec: it suppresses questions, while controlled studies show that asking on genuinely ambiguous work is one of the largest single gains available. The recommended rewrite has five parts. First, replace the LLM coordinator with a stateless dispatcher script over Orca's `--json` verbs, with the Orca task DAG as the only work state. Second, make one Task per `mvc` item the default and split only into independent or strictly serial Tasks. Third, drop gates entirely, because DAG dependencies already park dependent work, and let a worker that hits a one-way door end its attempt with the question. Fourth, move the worker addendum into a short repo-owned `WORKFLOW.md`. Fifth, make the final checks deterministic before adding any reviewer agent. This removes the gate and live-coordinator questions, turns the fallback for a long-blocked `ask` into the main design, makes the base branch of dependent work the central ruling, and raises new unknowns, mostly about whether a script outside an Orca terminal can drive Orca. The evidence base is uneven. MAST, ImpossibleBench, METR's maintainer study, UTBoost and the AGENTS.md study are controlled. Most claims about orchestration architecture rest on vendor engineering posts and 2026 preprints with no head-to-head benchmark. OpenAI's headline "500% more landed PRs" carries no quality data.

## Symphony is a level-triggered reconciler, not an agent system

Symphony's orchestrator contains no model. It is a daemon that polls a tracker. On each tick it reconciles the issues already running, then dispatches eligible issues in priority order while slots remain. Every worker outcome goes through **one state authority**: "The orchestrator is the only component that mutates scheduling state" ([SPEC §7](https://github.com/openai/symphony/blob/main/SPEC.md)). All judgement lives in a repo-owned `WORKFLOW.md`, made of YAML front matter plus a strict Liquid prompt template. The file is hot-reloaded, and an invalid edit keeps the last good config ([SPEC §5–6](https://github.com/openai/symphony/blob/main/SPEC.md)). The unit of work is **one issue → one workspace → one agent thread**. That thread does everything in sequence, from planning and self-review through to landing the PR ([elixir/WORKFLOW.md](https://github.com/openai/symphony/blob/main/elixir/WORKFLOW.md)). OpenAI's stated lesson is that "treating agents as rigid nodes in a state machine doesn't work well". They moved instead to giving agents "*objectives* instead of strict transitions" ([Blog](https://openai.com/index/open-source-codex-orchestration-symphony/)).

The details matter for the rewrite. A run counts as "succeeded" when it reaches a handoff state such as `Human Review`, not `Done`. Proof of work (CI green, a PR feedback sweep, walkthrough media) is **entirely prompt policy**, and Symphony itself verifies nothing ([SPEC §1, §11.5](https://github.com/openai/symphony/blob/main/SPEC.md)). Questions are actively suppressed. The high-trust example treats a user-input request as a hard failure. The prompt says "Do not ask a human to perform follow-up actions", and the only escalation is a "blocker brief" in a workpad comment plus a move to `Human Review` ([SPEC §10.5](https://github.com/openai/symphony/blob/main/SPEC.md); [WORKFLOW.md](https://github.com/openai/symphony/blob/main/elixir/WORKFLOW.md)). Nothing distinguishes "ready for review" from "needs your input" without reading prose. Dependencies are a dispatch gate rather than a scheduling graph. The Linear adapter marks a `Todo` issue non-dispatchable while a blocker is non-terminal, but once work starts, blockers are ignored ([elixir/README.md](https://github.com/openai/symphony/blob/main/elixir/README.md)). (One secondary note claims `blocked_by` never gates dispatch. The current SPEC and adapter docs show it does, through the adapter's `dispatchable` flag.) Decomposition is just another ticket: a planning issue whose output is more issues with blocker links. Agent-filed follow-ups land in `Backlog`, so a human must promote them ([Blog](https://openai.com/index/open-source-codex-orchestration-symphony/)).

Symphony has three known weaknesses. **It has no retry cap or dead-letter state**: an issue that keeps failing retries every ≤5 minutes until a human moves it ([SPEC §8.4](https://github.com/openai/symphony/blob/main/SPEC.md)). **Its scheduler state is in memory only**: it recovers from the tracker and the filesystem, not from a database ([SPEC §14.3](https://github.com/openai/symphony/blob/main/SPEC.md)). **It loses mid-flight steering**, which OpenAI concedes: "Sometimes the agent produced something that completely missed the mark" ([Blog](https://openai.com/index/open-source-codex-orchestration-symphony/)). The community reception focuses on what Symphony leaves out. Analysts warn that "generation scales effortlessly, validation does not" ([InfoWorld](https://www.infoworld.com/article/4164173/openais-symphony-spec-pushes-coding-agents-from-prompts-to-orchestration.html)). Practitioners report it is "*VERY* token hungry" ([X](https://x.com/daniel_mac8/status/2048845594756522365)). HN commenters call it an outer loop that "doesn't deliver the harness you need to make working software" ([HN](https://news.ycombinator.com/item?id=47252045)). The **500% landed-PR figure** covers "some teams" over three weeks and comes with no rework, defect or review-time data. Treat it as a volume anecdote, not as evidence of quality.

## The evidence backs three of Symphony's four bets

| Design choice | Symphony | Current Orca spec | What the evidence says | Strength |
|---|---|---|---|---|
| Orchestrator | Deterministic code | LLM coordinator | Favours code for control flow; LLMs at bounded decision points | Medium (taxonomies, vendor docs; no head-to-head) |
| Unit of work | One agent, one objective, whole ticket | Coordinator slices one change into parallel Tasks | Favours one writer per coherent change; parallelism across independent units | Medium |
| Roles vs objectives | Objective | Objective-ish (no roles), but coordinator is a role | Favours objectives; role specs fix little | Medium |
| Human escalation | Suppressed; blocker brief | One-way-door `ask` + gates | Favours asking on real ambiguity, front-loaded | Medium–Strong |
| Verification | Prompt policy only | Integration check + report; reviewers deferred | Tests pass ≠ correct; needs independent check | Strong |
| Repo policy | WORKFLOW.md, hot-reloaded | Worker addendum in each spec | Supports lean repo policy; long files cost more than they return | Medium–Strong (one controlled study) |

**Single versus multi-agent.** The best controlled evidence finds that role structure adds little once the base model is strong. MAST annotated 1,600+ traces across seven frameworks. Multi-agent systems failed **41–86.7%** of the time. Failures came mostly from **system design (~44%)** and **inter-agent misalignment (~31%)**, while "disobey role specification" accounted for only **1.5%**. On ChatDev, a task-objective verification step helped (+15.6 points) more than better role specs did (+9.4) ([MAST](https://arxiv.org/html/2503.13657)). Xu et al. found that a single agent matched homogeneous multi-agent workflows on seven benchmarks, at lower cost ([arXiv 2601.12307](https://www.arxiv.org/pdf/2601.12307)). The scaling study across 260 configurations found the multi-agent effect ranging from **+80.8% on decomposable tasks to −70% on sequential planning**, with returns diminishing as single-agent capability rises ([arXiv 2512.08296](https://arxiv.org/abs/2512.08296)). A ~100-line bash-only agent with no roles scores **>74% on SWE-bench Verified** ([mini-swe-agent](https://github.com/SWE-agent/mini-swe-agent)). Two caveats apply. MAST's traces come from 2024-era models, and no study compares N agents on slices of one feature against one agent on the whole feature.

**Parallel slices of one change are the specific thing the field warns against.** Cognition's core rule is that "actions carry implicit decisions, and conflicting decisions carry bad results". Its 2026 update says multi-agent setups work only "when writes stay single-threaded" ([Cognition 2025](https://cognition.com/blog/dont-build-multi-agents); [Cognition 2026](https://cognition.com/blog/multi-agents-working)). Anthropic notes that "most coding tasks involve fewer truly parallelizable tasks than research", and that its multi-agent system used about **15× the tokens of chat** ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). Claude Code's own docs say sequential or same-file work suits a single session better ([agent teams](https://code.claude.com/docs/en/agent-teams)). This weighs directly against the spec's coordinator that "slices the shape into Tasks". Slicing for parallelism inside one `mvc` item creates the semantic-conflict and integration problem that the spec then has to solve.

**LLM versus deterministic orchestration.** No benchmark compares the two head to head, but every signal points the same way. LLM coordinators show MAST's top failure modes: step repetition (15.7%), unawareness of stopping conditions (12.4%) and premature termination (6.2%) ([MAST](https://arxiv.org/html/2503.13657)). Claude Code documents "task status can lag … blocks dependent tasks" and leads that stop early ([agent teams](https://code.claude.com/docs/en/agent-teams)). Cognition finds LLM managers "default to being overly prescriptive" ([Cognition 2026](https://cognition.com/blog/multi-agents-working)). A 2026 preprint argues that control-flow hallucination is an architectural consequence of giving loops to a probabilistic system ([arXiv 2606.15874](https://arxiv.org/abs/2606.15874)). The current spec's coordinator mostly does bookkeeping: create Tasks, dispatch, record rulings, release workers, run checks. Every one of those jobs is deterministic.

**Roles versus objectives.** Anthropic's guidance is to avoid "hardcoding complex, brittle logic" while still giving "concrete signals", because "smarter models require less prescriptive engineering" ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Delegation still needs an objective, an output format and explicit boundaries ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). This matches the spec's Task-spec contract. A "role" is justified only when it buys **context isolation**, and the clean-context reviewer is the clearest case. Cognition reports such a reviewer finds about 2 bugs per PR, ~58% of them severe ([Cognition 2026](https://cognition.com/blog/multi-agents-working)). No rigorous ablation of goal-only versus step-by-step prompting exists. This conclusion rests on vendor guidance and indirect benchmark results.

**Repo-resident policy.** The only controlled study found that LLM-generated context files *reduced* success by 0.5–2% and raised cost by 20–23%. Developer-written files gave **~4%** more success at up to 19% more cost. Agents obey these files faithfully, so every extra instruction makes the task harder ([arXiv 2602.11988](https://arxiv.org/html/2602.11988v1)). `WORKFLOW.md` is therefore a good idea only if it stays short: commands, hard rules, the door list and the report format. It should not become a style guide.

## Asking beats Symphony's silence, but front-loaded and cheap

On escalation the spec is better grounded than Symphony. On an underspecified variant of SWE-bench Verified, letting the agent ask improved performance by **up to 74%**, but "models struggle to distinguish between well-specified and underspecified instructions" ([Ambig-SWE](https://arxiv.org/abs/2502.13069v3)). A dedicated ambiguity check before execution raised resolve rates from about 61% to **69.4%**, at roughly 1.7× the cost ([Ask or Assume](https://www.alphaxiv.org/abs/2603.26233)). When agents were given an explicit option to flag or abort, test cheating dropped from **54% to 9%** for GPT-5 ([ImpossibleBench](https://arxiv.org/html/2510.20270)). Anthropic's telemetry finds only **0.8% of agent actions appear irreversible**. It recommends making sure humans can monitor and intervene, rather than requiring approvals ([Anthropic](https://www.anthropic.com/research/measuring-agent-autonomy)). Taken together, this supports the spec's door rule. Because `mvc`'s grill settles ambiguity before code is written, it already plays the role of the "Intent Agent". The one-way-door ask is the residual channel. The one-way/two-way framing itself is practitioner usage without a primary citation.

What the evidence does *not* require is a blocking, gated, mid-flight channel. Supervision capacity is limited by **evaluation bandwidth**. Practitioner ceilings sit at 3–5 parallel threads, which agrees with OpenAI's "three to five sessions" and with Claude Code's 3–5 teammates. All of these figures are anecdotal ([Osmani](https://addyosmani.com/blog/cognitive-parallel-agents/); [Blog](https://openai.com/index/open-source-codex-orchestration-symphony/); [agent teams](https://code.claude.com/docs/en/agent-teams)). The spec's batched-inbox model fits this. The gate machinery around it does not pay for itself, for a structural reason. **DAG dependencies already park dependent work.** If the worker on Task S1 stops with a question, every Task depending on S1 stays `pending` until S1 completes. A gate adds parking only for Tasks that are *not* DAG-dependent on the asker, and those by definition do not need the answer. Orca's own guide also says "Do not create a gate merely to answer a worker's `ask`" (Orca 1.4.221 orchestration guide, `references/messaging-and-gates.md`). The simpler design is the spec's fallback for a long-blocked `ask`, promoted to the primary path. A worker that hits a one-way door writes the question in `mvc` format plus a **Meanwhile** line to its report file, and ends with `worker_done --outcome failed`. That outcome is Symphony's blocker brief made structured. The owner rules in a batch window and the ruling is appended to the rulings file. A retry with `--retry-of` then starts a **fresh attempt** from the ruling. This mirrors Symphony's "Rework is a full approach reset", and context-rot evidence prefers fresh sessions rebuilt from durable artifacts over long-held contexts ([Chroma](https://www.trychroma.com/research/context-rot); [Anthropic harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). This design has two costs. It discards in-progress work on the asking Task, which is cheap if one-way doors surface early. And it interacts with Orca's **3-failure circuit breaker**, which needs testing.

## Tests passing is the weakest link in both designs

Symphony's proof of work and the spec's integration check both lean on signals that controlled studies show to be weak. On impossible tasks, frontier agents cheated about **half the time** (GPT-5 54%, Opus 4.1 50%), and LLM monitors caught only **42–50%** of it ([ImpossibleBench](https://arxiv.org/html/2510.20270)). Augmented tests revealed that **15.7%** of passing SWE-bench Verified patches were wrong ([UTBoost](https://arxiv.org/html/2506.09289v1)). METR's maintainers merged test-passing AI patches at rates **24.2 points below** the automated grader, with code quality the most common reason for rejection ([METR](https://metr.org/notes/2026-03-10-many-swe-bench-passing-prs-would-not-be-merged-into-main/)). AI pre-review anchors human reviewers: they find more trivial issues, no more severe ones, and save no time ([USI](https://www.inf.usi.ch/en/node/11023)). Symphony's walkthrough videos have **no evidence** that they reduce review burden, and the "complexity analysis" in its README appears nowhere in the published policy.

This leads to an ordering for the rewrite. **Deterministic checks come first, owned by the dispatcher rather than the agent.** These are the lint, test and build commands from `WORKFLOW.md`, run on the final branch, plus two cheap diff checks that need no model. The first flags any changed test file, which maps to the spec's "test contracts" door. The second flags any file outside the shape's touchpoints, which maps to report bin 2. Neither diff check has been tested in the literature, but both target failure modes the studies measured. Next comes the worker's report as proof of work at `--report-path`, ordered surprise-first. The clean-context **surprise check** stays deferred for now, but it is the best-supported addition. Verification is ~23.5% of MAST failure mass, independent review beats self-review, and it is the only detector for a one-way door the worker never asked about. When added, it should be a DAG node: a Task depending on the implementation Task, with the objective "list what a reader holding only the shape and rulings would not expect". It should not be a persona. The spec's trigger (first escape or first unlogged decision) is reasonable. Bring it forward if the deterministic diff checks fire often.

**On the METR productivity figures in the spec's "Why this shape" section.** The original RCT (16 developers, 246 tasks) found developers **19% slower**, while they believed they were 20% faster ([METR](https://metr.org/blog/2026-02-24-uplift-update/)). The late-2025 follow-up reported **−18%** for returning developers (CI −38% to +9%) and −4% for new ones. Under METR's sign convention, where +19% meant slowdown, **a negative value is a speedup**. Some secondary write-ups misread it as an "18% slowdown" ([particula.tech](https://particula.tech/blog/metr-reversed-19-percent-slower-ai-coding-study)). METR itself calls the follow-up "an unreliable signal", because 30–50% of developers skipped tasks they would not do without AI, and it is redesigning the study ([METR](https://metr.org/blog/2026-02-24-uplift-update/)). The spec should cite METR only for the **perception gap**, which is what it uses it for, and not as a speed estimate in either direction.

## The rewrite: a stateless dispatcher over the Orca DAG

The Orca DAG can stand in for Symphony's tracker without adding a second store. Symphony's tracker contract is deliberately thin: list items by state, refresh items by ID, and let the adapter compute `dispatchable` ([SPEC §11](https://github.com/openai/symphony/blob/main/SPEC.md)). Orca Tasks already offer statuses (`pending, ready, dispatched, completed, failed, blocked`), JSON dependency arrays, `task-list --ready`, readiness enforced at `worker-start` (`task_not_startable`), and `worker_done` auto-settlement with `--report-path` (Orca 1.4.221 CLI help). On dependencies Orca is *stronger* than Symphony, because readiness is enforced rather than best-effort. It is also more durable: Run, Task and Dispatch state persist, and mutations are idempotent through `--retry-request`. What Orca lacks is tracker metadata (priority, labels, PR link), a review state distinct from `completed`, a concurrency cap, backoff, stall-kill and hot-reloaded policy. All of that is glue a script can supply.

| Concern | Recommended design | Replaces in current spec |
|---|---|---|
| Orchestrator | Stateless `dispatch-tick` script run by launchd/cron. Each tick: `task-list --ready --json` → cap by `worker-list --terminal-state active` count → `worker-start --task … --worktree new-top-level --json` → `worker-list --terminal-state reclaimable` → `worker-release`. No LLM; holds no state between ticks | LLM coordinator, coordinator prompt, live-session risk |
| Work state | Orca Tasks only; priority as a title prefix sorted by the tick | Unchanged constraint ("Orca is the only task state") |
| Unit of work | Default **one Task per `mvc` item**. Split only when the shape names independent parts (parallel) or a strict sequence (serial chain); the split is written in the shape and loaded deterministically | Coordinator slicing |
| Dependent base | A dependent Task branches from its parent's branch, or from `main` after the owner lands the parent | Open question on integrating slices |
| Review/landing state | `completed` + report = Symphony's "Human Review". Optionally an owner-only `land` Task per item that dependents depend on | Implicit |
| One-way door | Worker ends `--outcome failed` with the question in its report; owner rules in a batch; retry with `--retry-of` from a fresh context | `ask` + `gate-create` + `gate-resolve` + `reply` |
| Three-door stop | The tick counts question-outcomes per item and stops dispatching at the threshold | Coordinator judgement |
| Policy | Repo `WORKFLOW.md`: front matter (agent, model, concurrency cap, base branch, check commands) read by the tick; short body (door list, ask format, assumption logging, tests-first, report order). Each Task spec says "read and follow `<repo>/WORKFLOW.md`", so edits take effect on the next attempt | Worker addendum appended per spec |
| IDs | Loader assigns `R…` and `S…` deterministically from the shape; workers number assumptions per Task (`S1/A1`); the inbox skill numbers rulings `D…` when appending | Coordinator numbering |
| Stalls | No kill on silence. A stale heartbeat goes to the inbox as an escalation; stop only on positive evidence. The 3-failure breaker caps attempts, a cap Symphony lacks | Unspecified |
| Follow-ups | Worker lists proposed follow-ups in its report; the owner creates Tasks. Workers never write the DAG | Unspecified |

Three points of steelmanning keep this honest. First, the LLM coordinator has one real advantage: **judgement at decomposition time**, deciding how to slice a shape. The rewrite moves that judgement into the `mvc` grill, where the owner already sits, rather than giving up on it. If shapes cannot express a split, a Symphony-style *planning Task*, whose output is proposed Tasks for owner approval, is the fallback, and it keeps the loop deterministic. Second, one Task per item makes each run longer, and context rot is real ([NoLiMa](https://proceedings.mlr.press/v267/modarressi25a.html)). The mitigation is Anthropic's harness pattern of one feature per session, with progress persisted in files and git, together with the spec's existing WIP ceiling. Splitting into parallel writers is not the mitigation. Third, Orca's "absence never authorizes action" rule conflicts with Symphony's stall-timeout kill. The rewrite follows Orca, which trades automatic recovery for safety. That costs the owner a touch when an agent hangs while still alive.

### Open questions under the rewrite

The gate questions, the live-coordinator question and the hours-long `ask` question disappear with the rewrite. These remain or are new:

| Question | Kind | Note |
|---|---|---|
| Can a process outside an Orca terminal (launchd/cron) run `task-list`, `worker-start`, `worker-list`, `worker-release` without a session handle? | Smoke test | Decides script versus automation-hosted tick; automations launch only agents |
| Does `worker_done` settle the Task (visible to `task-list --ready`) without the Run inbox being consumed? Can the owner be the Run's inbox consumer while the script only reads state? | Smoke test | If yes, consumer fencing stops mattering |
| Does a question-ending `--outcome failed` count toward the 3-failure circuit breaker, and does `--retry-of` after a ruling reset it? | Smoke test | Decides whether questions need their own outcome encoding |
| Can an unattended worker finish with no permission prompt, and is a push from its worktree refused? | Smoke test | Unchanged from the earlier spec |
| How does the inbox list every Task whose last attempt ended with a question, across open Runs (`run-list` → `task-list --status failed --run`)? | Smoke test | Replaces listing open gates |
| When does an `mvc` item split into multiple Tasks, and how does the shape express parallel versus serial parts? | Ruling | Evidence: split only for independence or strict sequence |
| What does a dependent Task branch from: its parent's branch (stacked) or `main` after the owner lands the parent? | Ruling | Stacked branches are the field's direction ([Graphite](https://graphite.com/guides/graphite)) |
| Does the `mvc` export carry every field the loader reads, plus the split and requirement IDs? | Check | The loader depends on it |
| Deterministic diff checks (test files touched, files outside touchpoints) in the tick's final check | Build | Cheap, model-free partial surprise check |

## Conclusion

Most of the complexity in the current spec, including gates, gate-on-ask, inbox fencing and coordinator liveness, exists because an LLM sits in the control loop and the work is sliced finer than the evidence supports. Remove both and the remaining design is close to what Symphony would look like if it were built on Orca. In some ways it is better than Symphony: a durable DAG with enforced readiness, a retry cap, and a structured question channel where Symphony has prose blocker briefs. The owner's three touches survive unchanged. The grill gains a job (deciding the split), and the gate ruling becomes a batch ruling followed by a retry.

The bigger risk now sits outside orchestration. Every controlled study on verification says a passing check does not mean the code is mergeable. Symphony's critics land on the same gap: it orchestrates well but has no inner quality harness. The trial should therefore measure escapes and diff-check flags more carefully than throughput. Whether the clean-context reviewer joins the core design should be decided by those numbers, not by OpenAI's 500%.
